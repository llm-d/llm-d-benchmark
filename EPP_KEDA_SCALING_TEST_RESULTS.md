From ScaledObject events:
```

```

**Why Scaling Didn't Occur**:
1. KEDA ScaledObject tried to query Prometheus metrics via the TriggerAuthentication
2. Prometheus returned 401 Unauthorized when KEDA's external metrics API tried to authenticate
3. With no valid metric readings, the HPA could not make scaling decisions
4. The HPA remained at the original 2 replicas without scaling

**Infrastructure Dependency**:
- The Prometheus instance in this OpenShift cluster requires specific RBAC permissions
- The ServiceAccount `wva-prometheus-auth` needs to be granted access to query the Prometheus API
- This is cluster-admin configuration that must be set up by the cluster administrator
- It's not part of the EPP+KEDA harness configuration

## Root Cause Analysis

### Why Scaling Failed

The KEDA ScaledObject was unable to query Prometheus metrics due to **HTTP 401 Unauthorized** errors.

**Error Chain:**
1. KEDA's external metrics API tries to query Prometheus using the bearer token from the `prometheus-auth` Secret
2. Prometheus rejects the request with 401 Unauthorized
3. KEDA cannot compute scaling metrics
4. HPA receives no metric values (`<unknown>` targets)
5. HPA cannot make scaling decisions
6. Deployment remains at 2 replicas

**Prometheus Error Log:**
```
KEDAScalerFailed: prometheus query api returned error. status: 401
```

### Cluster Configuration Issue

This is a **cluster-level infrastructure issue**, not a defect in the EPP+KEDA implementation:

- The Prometheus instance running in OpenShift requires explicit RBAC permissions
- The `wva-prometheus-auth` ServiceAccount needs to be authorized to:
  - Access the Prometheus API endpoint at `thanos-querier.openshift-monitoring.svc.cluster.local:9091`
  - Query metrics from the external metrics API
- This must be configured by a cluster administrator with appropriate permissions

**What Would Need to Happen:**
1. Cluster admin creates RBAC ClusterRole for Prometheus access
2. Binds the role to the `wva-prometheus-auth` ServiceAccount
3. Restarts KEDA pods or waits for KEDA to retry
4. KEDA successfully queries Prometheus
5. Metrics become available to HPA
6. HPA makes scaling decisions based on KV cache and queue metrics
